# Recorded order removal

`POST /ops/orders/:id/remove` is Super Admin only. Operations, test Operations,
clients, shops and riders cannot remove orders. This is an audited visibility
removal for test cleanup; it does not cancel an order, refund a payment, release a
payout, change an order-flow rule or destroy an order. There is no restore or bulk
removal endpoint.

```json
{ "reason": "Retire unfinished test order", "confirmEmail": "client@example.com" }
```

The trimmed reason must contain 1–2,000 characters. `confirmEmail` must exactly
equal the client's current database email, including case and whitespace. It is
never normalized. Super Admin order projections include `clientEmail` from that
client row for the confirmation dialog. Other roles do not receive this field.

Success is `200 { "id": "ord_...", "removedAt": "<ISO timestamp>" }`.

| Status | Error | Meaning |
| --- | --- | --- |
| 403 | `forbidden` | The caller is not a Super Admin. |
| 404 | `order_not_found` | The order does not exist. |
| 409 | `order_already_removed` | A removal was already recorded. |
| 400 | `reason_required` | Reason missing, blank, not text or too long. |
| 400 | `confirm_email_mismatch` | Exact client email was not supplied. |
| 409 | `order_removal_blocked` | Financial or assignment protection; includes a plain-language `message`. |

## Eligibility and financial protection

Removal is permitted for simulated orders whose client is still a test account
(`order.reviewData` and `client.reviewData` are both true), or real orders with no
submitted/confirmed payment and no shop assignment, including job assignments.
Simulated payment flags are generated by the server, never trusted from removal
request JSON. There is no status-based shortcut around these checks.

Every order remains blocked if it has a released payout, an active/completed
refund, a refund settlement or supplier remainder, a paid supplemental change or
delivery-pin transfer, an unresolved submitted supplemental transfer, an
order-linked credit movement, a voucher reservation/redemption/ledger entry, or a
platform revenue adjustment. A simulated order cannot hide actual money either:
its submitted/confirmed order and basket payments must carry the server's
`simulated` marker. Real orders with a shop remain subject to existing recovery
and cancellation rules. Blocked orders keep all existing visibility and behavior.

## What is kept and hidden

Migration `1794060000000_order_removals` adds an immutable removal record with the
order ID, actor, timestamp and reason. The order row, state, accepted snapshots,
payments, payouts, invoices, lines, jobs, cases, messages, files and audit history
are retained. Removal never transfers or adjusts money. The removal marker and
`order.remove` audit commit under the same domain transaction and advisory lock.
The global staff audit remains available; order-scoped audit reads return 404.

The compatibility store and all scoped read graphs share the active-order SQL
filter in `src/order-removal.js`. Removed orders and their children are absent
from staff/party lists, details, queues, notifications, finance/report aggregates,
shop scheduling and matching workload. Order details and order-scoped chats,
calls, receipts and exports return 404. Checked-out carts, associated quote and
sample records are hidden. A shared basket and its combined receipt are hidden
when a member is removed, so their immutable receipt cannot expose the removed
group, regardless of its position. Its checked-out cart is hidden too. Active
sibling orders remain readable, but per-order payment submit/confirm/reject
returns `409 basket_payment_unavailable` with a plain-language message. Immutable
basket membership is retained in a non-public guard lookup; no payment or
receipt snapshot is rewritten. Client pricing privacy also uses the invoice's
own basket marker, independently of the public basket graph. Existing app URLs
and other response shapes remain compatible.

The marker is inserted before the active graph is reloaded and saved, so save
maintenance cannot act on the removed order. Direct lifecycle candidate queries,
call reconciliation, chat cleanup and SQL funnel reporting also exclude removal
markers. Pending/sending order push-outbox records are suppressed. Removal emits
silent realtime invalidates (including `orders`) for open queues and counts; it
creates no client, shop or rider inbox/push notification. Historical messages and
call records remain in storage. Existing open-case file-retention protections
continue to apply to retained evidence.

## Read-boundary review

- `src/postgres-store.js`: complete graphs, hot role/detail/queue graphs,
  production probes, client home/bootstrap, matching/cart, files, notifications
  and realtime/push delivery use the same filter. Hidden rows are absent from
  both persistence baselines and current graphs, so later saves retain them.
- `src/server.js`: issue-window, reschedule, shop-acceptance, hub, survey,
  first-order and call candidate queries exclude removed orders. In-memory
  finance, refunds, credits, invoices, offers, counts and lifecycle work consume
  the active graphs. Audit is deliberately exempt.
- `src/pricing-dashboard.js`: direct SQL funnel aggregates exclude removed order
  events; order money reporting consumes the active graph. Credit and voucher
  ledgers are never filtered away: their activity blocks removal.
- `src/order-calls.js`, `src/delivery-chat.js`, `src/pickup-chat.js` and
  `src/client-shop-chat-routes.js`: direct call/cleanup/thread-index reads exclude
  removals; order-scoped access still requires an active order.

Local HTTP regression coverage lives in `tests/order-removal-postgres.test.js`.
It launches the API on a free loopback port with test-only signed Clerk JWTs and
an isolated test database; it must never target production.
