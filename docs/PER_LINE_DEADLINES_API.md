API field contract for #189 (implementation in progress; PR targets `dev`). The payment decision is settled: **more than one sub-order means 100% upfront**, including one shop on different dates. One sub-order retains the configured 75% or 100% option. No new balance-payment flow.

- `POST /me/matches` and `/me/matches/next`: send the product's ISO date-time in `deadline`, plus `cartId` as today. An explicit date overrides the cart's legacy default; no `basket_deadline_mismatch`. Selection tokens bind that product's date. `groupId` restricts the shop; absent an explicit date it inherits that group's date.
- `POST /me/carts/:id/lines`: existing `{selectToken, matchRequestId, ...}` keeps the token's date. Direct listing requests may also send `deadline`. `PATCH /me/carts/:id/lines/:lineId` accepts `deadline` and rechecks that listing for the new date. A date conflicting with a supplied selection token is rejected. Dates are normalized ISO instants; send the same deadline instant for products intended for the same group.
- `cart.lines[].deadline` is the effective date. `cart.groups[]` groups by **shop + deadline**, with existing opaque `id`, `lineIds`, money fields, and new `deadline`. Same shop on different dates uses the same anonymous `label` (e.g. Shop A), with different group IDs. `cart.groupCount`, `cart.shopCount`, and `cart.isMultiGroup` are additive. Use `isMultiGroup`, not unique-shop count, to select grouped checkout.
- `cart.clientQuote.upfrontReason` is `multiple_fulfillment_groups` for >1 group, otherwise `platform_setting`. Existing `downpaymentPercent`, `downpaymentMinor`, and `balanceMinor` remain authoritative. Each delivery group pays its own delivery fee; hub pickup remains one fee per basket divided evenly across groups with stable integer remainder allocation. Fulfillment choice stays basket-wide.
- Legacy cart-level `deadline` remains a default for old clients/lines. Explicit line dates win. `cart.deadline` and `basket.deadline` report the shared date when all groups have one date, otherwise `null`. Existing single-date data remains supported.
- Checkout returns existing `{order, basket, invoice}` whenever there are >1 groups (including same-shop/different-date); one group retains `{order, invoice}`. `basket.groups[].deadline` and `invoice.groups[].deadline` identify each date. `basket` also has `groupCount`, `shopCount`, `isMultiGroup`, and `upfrontReason: multiple_fulfillment_groups`.
- Each underlying order exposes its own `deadline` in checkout and normal role-scoped order projections; jobs carry that deadline. Existing `readyBy`/`promiseBy` retain their shop-production/client-estimate meanings. Each sub-order keeps its independent job, fulfillment, escrow, refund, and payout. Combined receipt delivery rows also carry `deadline`; receipt sections use `orderId` as their unique key.

More than one group requires a date on every line (`400 basket_deadline_required` if missing). No payment/refund allocation changes beyond the approved 100%-upfront rule for multiple groups.
